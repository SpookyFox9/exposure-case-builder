The engineering workflow requires a search for existing work before building (step 0). This was **not done before the build started**; it was done on 2026-11-02 as part of the rules audit (`ENGINEERING_AUDIT.md`). This page records what it found and how we position the project.

**Consequence:** do not say Tenable lacks solution-level fix grouping, ticketing, an AI remediation agent or an MCP server; it has all four on Tenable One. The defensible difference is the portable, evidence-backed package an engineer can use without console access, the disjoint per-action accounting, the open scoring, and the decision record. Also true and checkable: this server is read-only except two local writes and changes no Tenable system, while Hexa's MCP server can create tickets, tags, dashboards and scans.

## Positioning

- Tenable's own product already covers fix grouping by solution (Solutions view), ticketing (Jira, ServiceNow) and an MCP server (Hexa AI), all on Tenable One licensing. State that plainly, then state the difference below. See "Tenable's own features".
- Do **not** claim novelty. Say instead: *similar problems are addressed by Patch Shepherd, the Chokepoint family and the vetted Remediation Priority & Impact Agent; this project's difference is a two-view design (risk cases and CPE-keyed fix packages, linked both ways), a threats-versus-backlogs queue, a deterministic stdlib engine with an MCP surface, and a local decision log.*
- The honest gap against the Chokepoint family: it credits shared fixes **once** across the whole shortlist (marginal coverage) and searches for a short ordered set. Our packages are disjoint by construction, so there is no double counting. We now offer a greedy host-clearing order (`coverage`, below) but it is a heuristic over packages, not a search for the shortest set of actions.
- **Coverage order (built 2026-11-03).** `fix_queue(order="coverage")` borrows the idea of greedy ordering from the Chokepoint family but is not the same algorithm. Chokepoint solves weighted maximum coverage over an action-to-findings matrix. Our packages already partition findings, so the overlap we can credit once is **hosts**: a package's gain is the number of hosts it newly brings to zero urgent findings, given the packages already placed. That is an all-of condition, not set cover, so there is no approximation guarantee, and we do not claim the shortest plan. Chokepoint's ticket payload, plan hash and execution receipts are not built.
- Patch Shepherd diffs against the previous pull to show trend. We now have a read-only `trend_diff` against a saved earlier export (built 2026-11-03): finding-id based, with host overlap beside every count, absence never reported as a fix, and counters for id instability. It does not archive pulls for you, has no per-case or per-package deltas yet, and has not been run against two real pulls.

## Reuse

No code was reused. Patch Shepherd, the Chokepoint family and most others are MIT; `tenable-sc-mcp-server` is GPL-3.0-only and `sc-ai-agent` is BSD-3-Clause, so reusing those would carry obligations. Ideas acknowledged: clustering by shared fix (Patch Shepherd, Chokepoint), marginal coverage (Chokepoint), aggregation with provenance (Tenable CTEM MCP).

## Library decision: pyTenable

Evaluated 2026-11-02 from PyPI metadata: pyTenable 26.10.1, MIT, **requires Python >= 3.11**, 14 runtime dependencies (requests, pydantic, marshmallow, gql, graphql-core, python-box, arrow and others). Our fetch path is four endpoints and the project promises Python >= 3.10 and one runtime dependency. **Decision: keep the stdlib client.** Revisit if the fetch surface grows (pagination, retries, other Tenable products). The community Tenable MCP server builds on pyTenable.

## Other Exchange listings and repositories read (2026-11-04)

Read on the morning of 2026-11-04: the open Exchange listing PRs #221-#226 and the READMEs (not the code) of the repositories this page had listed as unread (the Chokepoint Finder repositories, `compliance-prioritizer`, `tenable-tag-optimizer`, `tenable-exposure-alert-notifier`, `cyber-risk-quantifier`, `navi-skills` and `tenable-sentinelone-patch-remediation-bridge`). READMEs describe a project; claims were not run or verified.

- **Vuln Prioritizer** (alkaf499, Exchange PR #225, skill plus CLI, MIT, stdlib-only at runtime) is the closest neighbour. It reads a `navi.db`, scores **each finding** with a two-layer model (impact from a CVSS fallback chain crossed with probability from VPR, then EPSS, with CISA KEV as a floor; then one tier shift from asset context in a CMDB overlay), and writes a tiered worklist with SLAs and due dates, an executive report and CSVs. It enriches from external feeds (Metasploit, Exploit-DB, Nuclei; optional EPSS and GitHub PoC lookups), flags `vpr_low_but_exploited` divergences, replays enriched runs byte-for-byte from a frozen cache, and lets an LLM propose asset classes but keeps it out of scoring. Not described: grouping findings into fix units, per-action "what this alone clears", an engineer handoff per fix, a decision log, or an MCP server. **Difference:** it ranks findings and sets deadlines; this project groups findings into cases and fix packages and hands each package to the engineer who applies it. It has SLAs, asset context and external exploit feeds, which this project does not.
- **RiskProof** (PR #222, MCP): investigates Tenable or Nessus findings with EPSS, KEV and GreyNoise, operator-supplied asset context, allowlisted live validation checks (TCP, banners, TLS), and P1-P4 decisions in an HTML report. It touches targets on the network; this project never does.
- **SecOps Autopilot** (PR #223, skill): drives one CVE through KRI scoring, approval-gated ticketing, containment and patching, then verifies with a fresh Tenable read. A per-CVE response workflow with external actions, not a fleet-wide triage view.
- ScreenWarden (#226, Android agent guardrail) and maskline (#221, secret redaction for transcripts) are unrelated.
- **Later listing PRs (titles and descriptions read 2026-11-04 evening via `gh`, repositories not read):** **ThreatWeave AI** (#228, sreedhar51) is a deterministic per-asset queue that correlates VM or SC findings with failed CIS checks, writes Decision Receipts with replay, and uses Claude for briefs only. **RBVM Agent** (#229) groups findings by policy into SQLite and manages Azure DevOps cards. **Porygon Mitigator** (#233) finds findings reachable through firewalls and plans mitigations. **Exception Guardian** (#235) re-grades risk exceptions against KEV and EPSS. **Exposure Radio** (#236) diffs two VM exports into a spoken briefing, separating new exposure from new visibility (the same distinction as our `newly_visible`). Also reported by a separate research pass (not re-verified): Cyber Risk Quantifier (dollar loss per finding) and BOD 26-04 Risk Tiering (Hexa MCP plus CISA Vulnrichment).
- **Chokepoint Finder** family (READMEs read): confirms the table above. Greedy weighted max-coverage over synthesized actions with marginal credit, fail-closed evidence gates (missing evidence reads `UNKNOWN` and holds), plan-hash-bound approvals with one-time receipts, and verification that re-queries the source. Far more machinery on the act-and-verify side than this project, which stops at the handoff and the recorded decision.
- **Tenable + SentinelOne patch remediation bridge** (jdelong-tenb): triggers a patch job through any patch tool's MCP server via a two-call contract, then releases EDR containment on a pass. Complementary: it executes a fix, while a fix package says which fix and where.
- **Cyber Risk Quantifier** (FAIR dollar estimates from a CSV export), **Compliance Prioritizer** (compliance benchmark failures, not vulnerabilities), **navi-skills** (driving the navi CLI), **tag optimizer** and **exposure alert notifier** (write tags or send e-mail): little overlap.
